# Nessus capability comparison

References checked on **14 October 2026** against official Tenable plugin pages
and documentation. No proprietary NASL source or Nessus installation was
available. This is a source/evidence capability comparison, not a side-by-side
scan benchmark or a claim that Nessus has no defects.

CCure's **15 network modules**, **57 network check areas**, **155 built-in
configuration rules**, database-loaded benchmark rules and external Nuclei
templates have different granularities. A module such as tls_scanner implements
many conditions; a dynamic matcher may cover many advisories; a collector can
serve many rules. Tenable describes its plugins as programs carrying detection,
vulnerability and remediation information, with authenticated configuration
assessment as another use. Raw counts therefore cannot establish equivalent
coverage. [Tenable's plugin model](https://docs.tenable.com/nessus/Content/AboutNessusPlugins.htm)

Statuses below refer to current CCure code and this audit's evidence. “Partial”
does not mean absent. “Unverified” does not mean a broken implementation.
P0/P1/P2 follow REPORT.md's roadmap, not a promise of feature delivery.

The comparison supports **breadth and control gaps**, not a numerical percentage
of Nessus parity. It also corrects several overly broad historical gap claims:
Windows SMB transport, database configuration, imported SCAP, privilege,
middleware and container checks already exist in current source and must not be
reported simply as missing. The new confirmed defects are narrower and testable.

Public protocol reference used to validate D05: [RFC4253 §7.1](https://www.rfc-editor.org/info/rfc4253/).
MongoDB's [hello command reference](https://www.mongodb.com/docs/manual/reference/command/hello/)
describes topology/handshake information; treating that alone as data-access proof
is an inference the CCure implementation makes, not a guarantee documented by
MongoDB. The reproducible ok:0 false-success predicate is independently shown
in characterize.py.
